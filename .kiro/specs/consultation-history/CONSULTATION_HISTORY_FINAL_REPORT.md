## 1. Резюме спецификации

Спецификация **Consultation History** задаёт систему просмотра, управления и взаимодействия с историей консультаций пользователя.

### Цели

- Пользователь может просматривать все прошлые консультации (таро, нумерология, сны, и т.д.).
- Фильтрация, поиск, пагинация, удаление, избранное.
- Экспорт (Premium) и шаринг (Platinum).
- Детальный просмотр, статистика, массовые действия.
- Адаптивность и доступность.

### Требования (requirements.md) — 12 шт.

| # | Требование | Кратко |
|---|------------|--------|
| 1 | View Consultation History | Страница `/history`, список консультаций (сервис, дата, вопрос, краткий результат), клик → детали, загрузка/пусто/ошибка |
| 2 | Filter and Search | Фильтры по типу сервиса и дате, поиск по вопросу/результату, подсветка, сброс |
| 3 | Pagination and Performance | Постраничный вывод (10–20), навигация, индикатор загрузки, обработка ошибок |
| 4 | Delete Consultations | Кнопка удаления, подтверждение, удаление из БД и из списка, обновление счётчика |
| 5 | Export (Premium) | Экспорт в PDF/JSON/CSV для premium/platinum, выбор формата и консультаций, upgrade для freemium |
| 6 | Favorites Management | Кнопка «избранное», фильтр «только избранное», синхронизация при удалении |
| 7 | Share (Platinum) | Поделиться ссылкой (platinum), просмотр по ссылке, отзыв ссылки, upgrade для не‑platinum |
| 8 | Consultation Details View | Полные детали, метаданные, действия (избранное, поделиться, экспорт, удаление), «назад» |
| 9 | Consultation Statistics | Сводка: всего, самый частый сервис, частота, первая/последняя дата, разбивка по сервисам |
| 10 | Bulk Actions | Чекбоксы, массовое удаление/избранное/экспорт, подтверждение, обновление списка |
| 11 | Consultation Sorting | Сортировка по дате (новые/старые), по типу сервиса, по избранному |
| 12 | Responsive and Accessibility | Адаптивная вёрстка, клавиатура, ARIA, контраст, скрытие колонок на мобильных |

### Задачи (tasks.md) — 4 фазы

- **Phase 1 — API (Backend):** единый/детальный/удаление/избранное/экспорт/шаринг/статистика/bulk (Tasks 1.1–1.10).
- **Phase 2 — Frontend:** HistoryStats, HistoryFilters, ConsultationCard, HistoryList, BulkActions, ExportDialog, ShareDialog, ConsultationDetail (Tasks 2.1–2.8).
- **Phase 3 — Pages:** страница History, страница детали, страница shared (Tasks 3.1–3.3).
- **Phase 4 — Integration:** tier-based доступ, unit/integration тесты, производительность, доступность (Tasks 4.1–4.5).

## 2. Текущее состояние («как теперь стало»)

### 2.1 Backend (API)

**Реализовано:**

| Endpoint | Сервис | Назначение |
|----------|--------|------------|
| `GET /api/tarot/history` | Таро | История раскладов с пагинацией (limit/offset), аутентификация |
| `GET /api/numerology/history` | Нумерология | История расчётов с пагинацией |
| `GET /api/iching/history` | И-Цзин | История консультаций с пагинацией |
| `GET /api/dreams/history` | Сны | История толкований с пагинацией |
| `GET /api/lenormand/history` | Ленорман | История раскладов с пагинацией |
| `GET /api/synastry/history` | Синастрия | История расчётов с пагинацией + проверка Premium/Platinum |

**Модели БД (хранение консультаций):**

- `TarotReading`, `NumerologyCalculation`, `IChingConsultation`, `DreamInterpretation`, `LenormandReading`, `Synastry` — все используются для истории.

**Сервисы:**

- В сервисах реализованы методы вида `get_reading_history()` / `get_calculation_history()` / `get_consultation_history()` / `get_dream_history()` / `get_synastry_history()` с пагинацией и привязкой к `user_id`.

**Не реализовано на backend:**

- Единый `GET /api/history` (фильтры: service_type, date_from, date_to, favorites_only; поиск; сортировка).
- `GET /api/history/[id]` — единая детальная консультация.
- `DELETE /api/history/[id]`.
- `POST /api/history/[id]/favorite` (в моделях нет поля `is_favorite`).
- `POST /api/history/export` (PDF/JSON/CSV, проверка tier).
- `POST /api/history/share` и `GET /api/shared/[shareId]`.
- `GET /api/history/stats`.
- `POST /api/history/bulk-delete`, `POST /api/history/bulk-favorite`.

Итого по API: история по каждому сервису с пагинацией есть; единый слой истории, удаление, избранное, экспорт, шаринг, статистика и bulk — нет.

### 2.2 Frontend (Web)

**Реализовано:**

| Элемент | Где | Описание |
|---------|-----|----------|
| **ResultActions** | `apps/web/src/components/ui/ResultActions.tsx` | Кнопки после результата консультации; опциональная ссылка «История» (`historyLink`). |
| **historyLink** | Страницы сервисов | На большинстве сервисов передаётся `historyLink="/history"` (таро, нумерология, и-цзин, руны, ленорман, синастрия, хорар, соляр, чакры, кармический); для снов — `historyLink="/journal"`. |
| **Dashboard — «Недавние консультации»** | `apps/web/src/app/dashboard/page.tsx` | Загрузка истории таро, нумерологии и снов через API (`getTarotHistory`, `/numerology/history`, `/dreams/history`), объединение, сортировка по дате, отображение до 10 последних с типом, заголовком, вопросом, датой. |
| **Journal** | `apps/web/src/app/journal/page.tsx` | Дневник практик: список записей, создание, фильтр по типу (сон, медитация и т.д.), теги, настроение; используется API журнала (не единый history). |
| **API-клиент** | `apps/web/src/services/api.ts` | `getTarotHistory(limit, offset)`, `getDreamHistory(limit, offset)`; остальные истории можно вызывать через `request('/numerology/history?...')` и т.д. |

**Не реализовано на frontend:**

- Маршрут **`/history`** — в приложении нет папки `apps/web/src/app/history/`; ссылки «История» ведут на несуществующую страницу (или пользователь попадает на заглушку, если настроен редирект).
- **`/archive`** — есть только заглушка: «Архив», «Страница в разработке».
- Компоненты: HistoryStats, HistoryFilters, ConsultationCard, HistoryList, BulkActions, ExportDialog, ShareDialog, ConsultationDetail.
- Страницы: `/history/[id]`, `/shared/[shareId]`.
- Единый запрос «вся история» с фильтрами/поиском/сортировкой на frontend не используется — только разрозненные вызовы по сервисам на дашборде.

Итого по frontend: есть единая точка входа «История» из сервисов и дашборд с недавними консультациями по трём сервисам; полноценной страницы истории и всего набора компонентов из spec нет.

---

### 2.3 Краткая сводка «как теперь стало»

- **Backend:** консультации по шести сервисам сохраняются и отдаются по отдельным history-endpoint’ам с пагинацией; единого API истории, удаления, избранного, экспорта, шаринга, статистики и bulk-операций нет.
- **Frontend:** с сервисов ведёт ссылка «История» на `/history`, но страницы `/history` нет; на дашборде показываются недавние консультации (таро, нумерология, сны); дневник снов/практик реализован отдельно (`/journal`). Остальные требования (фильтры, поиск, детали, экспорт, шаринг, статистика, массовые действия) на UI не реализованы.

То есть: **инфраструктура хранения и чтения истории по сервисам есть, единый сценарий «История консультаций» из spec реализован частично.**

## 3. Что дала реализация выполненных задач

Ниже — польза от уже сделанного (backend history по сервисам + интеграция ссылок и дашборда).

### 3.1 Сохранение и доступ к данным

- Все консультации по таро, нумерологии, и-цзин, снам, ленорман и синастрии пишутся в БД и привязаны к пользователю.
- Пользователь не теряет результаты после закрытия вкладки: их можно снова получить через API.
- Это основа для любой будущей страницы «История» и для аналитики использования сервисов.

### 3.2 Готовые API для истории по сервисам

- Шесть endpoint’ов с пагинацией (limit/offset) и проверкой пользователя.
- В синастрии добавлена проверка Premium/Platinum для доступа к истории.
- Уже сейчас дашборд может показывать «недавнее» без дополнительного backend; при появлении страницы `/history` те же API можно использовать для постраничной подгрузки по типу сервиса.

### 3.3 Единый UX-вход «История»

- Компонент ResultActions и параметр `historyLink` используются на многих сервисах.
- Пользователь везде видит одну и ту же кнопку/ссылку «История» (или «Дневник» для снов), что задаёт ожидание единого места для просмотра прошлых консультаций.
- После реализации страницы `/history` достаточно будет подставить её в `historyLink`.

### 3.4 Дашборд с недавними консультациями

- На дашборде отображаются последние консультации по таро, нумерологии и снам.
- Данные объединяются и сортируются по дате — прообраз единого «ленты» консультаций.
- Повышает вовлечённость: пользователь сразу видит свою активность и может захотеть перейти к полной истории.

### 3.5 Дневник практик (Journal)

- Отдельная полноценная фича: записи, типы, теги, настроение, список и создание.
- Для снов и смежных практик даёт ценность даже без единой страницы «История» и может в будущем быть связан с общей историей (например, фильтр по типу «сон»).

### 3.6 Основа для расширения

- Модели и миграции можно расширить (например, `is_favorite`).
- Поверх существующих history-endpoint’ов можно добавить единый слой (unified `/api/history`) с агрегацией и фильтрами, не переписывая хранение.
- Текущая реализация задаёт понятную архитектуру: «по сервису — свой history», «на фронте — единая страница и компоненты».

## 7. Рекомендации и следующие шаги

### 7.1 Критично для «как в spec»

1. **Страница `/history`**  
   - Одна страница, которая собирает консультации из всех сервисов (через существующие API или через новый unified API).  
   - Минимум: список (карточки), пагинация, базовый фильтр по типу сервиса.  
   - Затем: поиск, фильтр по дате, сортировка.

2. **Единый API истории (опционально, но желательно)**  
   - `GET /api/history` с параметрами: `service_type`, `date_from`, `date_to`, `favorites_only`, `search`, `sort`, `page`, `page_size`.  
   - Упростит frontend и позволит единообразно делать фильтры, поиск и сортировку.

3. **Детальный просмотр**  
   - Страница `/history/[id]` или модалка с полными данными консультации и кнопками (удалить, в избранное, поделиться, экспорт — по мере реализации backend).

4. **Удаление**  
   - Backend: `DELETE` по типу консультации и id (или единый `DELETE /api/history/[id]` с роутингом по типу).  
   - Frontend: кнопка в карточке/детали + подтверждение.

### 7.2 Важно для полноты фичи

5. **Избранное**  
   - Поле `is_favorite` в моделях, миграция, `POST .../favorite`, фильтр «только избранное», иконка в карточке.

6. **Статистика**  
   - `GET /api/history/stats`, компонент HistoryStats на странице `/history`.

7. **Экспорт (Premium)**  
   - `POST /api/history/export`, выбор формата (PDF/JSON/CSV), проверка tier, ExportDialog и кнопка «Экспорт».

8. **Шаринг (Platinum)**  
   - `POST /api/history/share`, `GET /api/shared/[shareId]`, страница `/shared/[shareId]`, ShareDialog, проверка tier.

### 7.3 Дополнительно

9. **Массовые действия**  
   - Bulk delete/favorite/export, чекбоксы, BulkActions.

10. **Тесты и качество**  
    - Unit-тесты для history API и ключевых компонентов, интеграционные сценарии (просмотр → фильтр → детали → удаление), проверка доступности и производительности.

## Итоговые выводы

- **Текущее состояние:** история консультаций по шести сервисам сохраняется и отдаётся через отдельные API с пагинацией; на фронте есть единая точка входа «История» и дашборд с недавними консультациями; отдельной страницы `/history` и полного набора функций из spec (фильтры, поиск, детали, удаление, избранное, экспорт, шаринг, статистика, bulk) пока нет.

- **Что дала реализация выполненных задач:** устойчивое хранение консультаций, готовые API для истории по сервисам, единый UX-вход «История», дашборд с недавней активностью и основу для быстрого доведения фичи до полного соответствия spec.

- **Чтобы «стало как в spec»:** нужны страница `/history` с списком и пагинацией, при необходимости — единый API истории, затем детальный просмотр, удаление, избранное, статистика, экспорт, шаринг и массовые действия с учётом tier’ов и тестов.

Данный отчёт можно использовать как единый источник правды по состоянию фичи «История консультаций» и план работ по её завершению.
